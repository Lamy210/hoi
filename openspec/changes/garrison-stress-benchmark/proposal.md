# 駐屯AIの最大規模性能検証ツールと探索計数

## 背景
PR #101で駐屯計画の同一州→目標への合法陸路重複探索をキャッシュしたが、削減回数以外のCPU時間・大規模の探索負荷は未測定。最大256配属師団・64防衛地点のシナリオを、毎回手で準備することなく同条件で実行できる計測基盤が必要。`package.json` の `npm run bench` は実行先 `tools/bench.ts` が存在しないため、現行のままでは動かない。

## 変更内容
- 実行可能な `tools/bench.ts` CLIを整備。最大256師団・64地点のシナリオをデフォルトに、反復回数・ウォームアップ回数・師団数・地点数・分布を指定可能。
- ベンチマーク専用 `createGarrisonStressWorld` は実際のmodern-eastasia州・隣接グラフを使用する。ただし通行可能性を切り離すため全州の支配者を日本へ統一する **合成** シナリオであり、本編の地理・領土条件の完全再現ではない。
- `stacked` は同一出発州に師団が集まった場合、`distributed` は出発州が分散した場合の負荷を計測する。
- `planGarrisonMoves` に非永続の任意メトリクス引数を追加し、初回選択と後段割当の合計で、経路lookup要求・実検索・キャッシュヒット・到達不能を記録する。
- ウォームアップを除いた `performance.now` の測定値からp50・p95・min・maxをレポートし、計画の決定論・WorldStateハッシュ不変・守備命令上限を検証する。
- CIでデフォルト最大規模を短い反復2回・ウォームアップ1回にてスモーク実行する。
- 計測の対象・制限・再現手順を `docs/garrison-performance-benchmark.md` に記載する。

## 選択肢と採用理由
- 何も計測せず大規模最適化を追加する：実際の性能退行と原因を切り分けられないため不採用
- 本番シミュレーション全体を1つのベンチにする：経路探索以外の影響が大きいため今回不採用
- 駐屯計画のオンデマンド合成ベンチを別ツール化：実行条件・探索回数・所要時間を分離できるため採用

## 非機能・セキュリティ・影響
- データはパックを読み込むNode.js開発用ツールで生成し、外部通信・本番保存・PIIを扱わない。
- `WorldState`、セーブ形式、移動AIの選択・操作、探索経路の合法性、週次4件上限は変更しない。
- 計測統計は呼び出し元のオブジェクトへ加算されるだけで、ユーザーが実行する通常のゲームには処理時間測定やメモリ操作を挟まない。
- 共有CIランナーの時間にはノイズがある。p95などの値を本番SLOや性能保証には使わず、ベンチマークの出力は証跡として扱う。
- 領土支配を一時的に統一しているため、現実の多国籍状態・海軍輸送・戦争中の経路有効性まで検証するものではない。
- 実メモリのピーク評価は未実装。heapDeltaはGCによって変動する参考値のみで、リーク判定には使用しない。

## 検証
- 256師団・64地点の生成と契約上限、配置が最大4命令に収まることをテストする。
- 小規模の2分布でp50/p95、実検索・ヒット数の整合、WorldState不変と決定論をテストする。
- CIで256師団・64地点を `npm run bench -- --iterations 2 --warmup 1 --format json` により実行する。
