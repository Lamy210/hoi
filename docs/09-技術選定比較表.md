- 状態: 確定（Phase 0 成果物 10/18）

## 2. シミュレーションエンジン言語の比較

| 候補 | 長所 | 短所 | 判定 |
| --- | --- | --- | --- |
| TypeScript | UIと同言語で単一コードベース。決定論は演算規律で担保可能（docs/08）。MODもJSエコシステムと親和 | 数値性能はRust劣位。型はコンパイル時のみ | **採用**（性能はSoA＋Workerで確保し、実測して不足分のみWASM化） |
| Rust + WASM | 最高性能・強い不変条件・決定論の自然さ | ビルド複雑化、MODとの連携層が必要、開発速度が遅い | **不採用（初期）**。ホットカーネル（経路探索・戦闘バッチ）の置換候補として再評価 |
| Go | 高性能・書きやすい | WASM二重環境・UI共有不可・エコサイズが二重管理に | 不採用 |
| ECS完全採用 | 大規模で柔軟 | 本作のエンティティは「州・国・師団」など少数種・固定関係で、汎用ECSの複雑さが過剰 | **データ指向設計（SoAストア）を部分的に採用**、フレームワークは導入しない（過剰設計回避） |

## 3. 地図描画の比較（調査結果に基づく）

| 候補 | 長所 | 短所 | 判定 |
| --- | --- | --- | --- |
| **MapLibre GL JS 6.18.0**（BSD-3） | インラインGeoJSONでオフライン描画可（タイルサーバ不要）。`feature-state` によるホバー/クロロプレスが公式手法。ラベル衝突エンジン内蔵。`tolerance` 簡略化 | 背後に地図エンジン（投影・タイル概念）。GeoJSON 2万ポリゴンの上限保証は非公開。細かい描画制御は効きにくい | **MVP採用**（〜数千プロヴィンス） |
| **PixiJS v8 8.23.0**（MIT） | WebGPU/WebGL2の薄い2D層。事前三角分割→単一バッファの頂点カラー更新で2万州の塗替えを設計できる。自由度最大 | ラベル衝突・投影・ピッキングはすべて自前実装。実装責務が重い | **後期候補**（20kプロヴィンス規模で評価。OpenFrontのバイナリterrain＋動的配色方式も参考に） |
| deck.gl 9.4.1 | GeoJsonLayer＋`pickable` で即座にホバー。バイナリ(typed array)経路 | オーバレイ志向（単体地図ではない）・依存が大きい（luma.gl） | 不採用（同機能をMapLibreで代替） |
| Canvas 2D 自前 | 依存ゼロ・学習容易 | 2万ポリゴン×60fpsは困難。GPU活用なし | 不採用（MapLibre導入で不要に） |
| WebGL生 | 完全制御 | 開発コスト過大（PixiJS/MapLibreで代替） | 不採用 |

**決定 D-004**: `world-map` 仕様には MapRenderer 抽象インターフェースを定義し、MVP実装をMapLibre、20k規模でPixiJS実装を追加できる構造にする。OpenFrontが示す「州をピクセル/タイル単位にする」方式は、LOD・ピッキング・配色更新が最もスケールするため、Phase 4 の性能評価で再判断する。

## 4. フロントエンド構成

| 候補 | 判定 | 理由 |
| --- | --- | --- |
| React 18 | 採用 | パネル・モーダル等の宣言UIに最適。エコシステム。地図は別レイヤーで分離 |
| Zustand | 採用 | UI状態（選択・パネル開閉・速度）の軽量ストア。Reduxの冗長さ回避 |
| Web Worker | 採用 | シミュ実行の必須構成（UIのフリーズ防止） |
| WebGPU/WebGL2 | 間接採用 | 描画ライブラリ（MapLibre/PixiJS）が管理。直接扱わない |
| Web Worker + SharedArrayBuffer | 不採用（MVP） | COOP/COEPヘッダが必要で静的ホスト制約が増える。postMessage転送で十分（Phase 4で再評価） |

## 5. バックエンド

| 候補 | 判定 | 理由 |
| --- | --- | --- |
| なし（クライアント完結） | **採用（MVP）** | シングルプレイヤー優先・低コスト・オフライン動作。セーブはIndexedDB |
| Bun + Hono | 採用候補（後期のみ） | MOD配布・マルチ調査時に最小構成で追加。常時稼働は最小限 |
| PostgreSQL/PostGIS | 不採用（実行時） | 地理データはパイプライン（ビルド時）で処理し、ゲームには同梱。実行時DBは不要 |
| SQLite | 採用候補（後期） | サーバ側の最小永続化（MODメタ・アカウント）用 |
| Redis / NATS / S3 | 不採用（現時点） | 常時稼働インフラの増設は要件に反する。マルチ実現時に再評価 |

## 7. OpenSpec と開発プロセス

- **OpenSpec 2.0.0（@fission-ai/openspec）採用**。`validate --strict --all` をCIゲート、`archive` でbaseline specへ反映。
- npm の無関係パッケージ `openspec`（プレースホルダ）と混同しないこと（docs/00 §3.1）。

## 8. LLM の位置づけ

- ランタイム必須コンポーネントには**しない**（要件どおり）。有料API常時稼働もしない。
- 検討用途: ①MOD制作時のイベント文章下書き（開発者ローカルツール・オプション）②翻訳支援（ビルド時）。いずれも生成物はリポジトリにコミットされ、ゲーム実行時はプレーンテキストとして読み込む。決定論・性能・コストに影響しない。

## 9. セキュリティ上の選定影響

- セーブ/MODの検証はエンジン層で実施（スキーマ・範囲・参照整合・チェックサム）。JS実行を含むMODはMVPで提供しない。
- CSP・厳格な `Content-Type`・`crossorigin` 設定はホスティング側で付与（PWA対応時は docs/14 Phase 5）。
