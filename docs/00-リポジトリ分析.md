### 3.1 OpenSpec の調査結果（運用ルールの根拠）

公式ドキュメント（openspec.dev/docs、github.com/Fission-AI/OpenSpec、npm レジストリ）を確認した結果:

- 正式パッケージは `@fission-ai/openspec`、現行バージョン **2.0.0**、MIT、Node ≥22.12.0。
- `openspec init`（`--tools none`）が生成する構成:
  ```text
  openspec/
  ├── config.yaml          # プロジェクト設定（schema: spec-driven）
  ├── specs/               # 能力(capability)ごとの仕様
  └── changes/
      └── archive/         # 完了Changeのアーカイブ先
  ```
- v2.0 では旧来の `openspec/project.md` は生成されず、後継は `config.yaml`。プロジェクト制約は `context:` に記述する。
- 仕様フォーマット: `### Requirement: <名前>`（本文に SHALL）＋ `#### Scenario: <名前>`（`- **WHEN** …` / `- **THEN** …`）。**各RequirementにはScenario最低1個が必須**（`validate --strict` でWARNINGは失敗扱い）。
- Changeフォルダ: `proposal.md`（Why / What Changes / Capabilities / Impact）＋ `tasks.md`（`## 1. グループ` + `- [ ] 1.1 …`）＋ `design.md`（任意）＋ `specs/<capability>/spec.md`（差分: `## ADDED/MODIFIED/REMOVED Requirements`）＋ `.openspec.yaml`（メタデータ: `schema/created/goal/affected_areas/skip_specs/retire_capabilities`）。
- 差分ゼロのChangeは `skip_specs: true` が必要。Requirement本文は500字以内（超過はWARNING、`--strict` で失敗）。
- アーカイブ（`openspec archive <change> -y`）で差分が `openspec/specs/<capability>/spec.md` にマージされる。

### 3.2 本プロジェクトの運用ルール（設計判断 D-002）

OpenSpec公式の哲学では `specs/` =「現在実装済み・合意済みの挙動」であり、グリーンフィールドでの `specs/` 事前投入は公式には案内されていない（確認した限り）。しかし本プロジェクトは「実装前に23領域の仕様を設計・レビューし、実装可否を判断する」ことを要件としている。そこで次の運用を採用し、`openspec/config.yaml` に明記する。

- **baseline 仕様**: `openspec/specs/<capability>/spec.md` に、23領域すべての「設計合意済みの目標仕様」を事前に作成する。ここには①システムの目的・責務・非責務②データモデル③計算規則④不変条件⑤依存関係に加え、**フェーズ非依存の契約レベル要件**（例: 「州の所有権と実効支配は別々に管理されること」「在庫は負にならないこと」）を書く。
- **Change の差分**: Phase 1 以降の各Changeは、そのフェーズで実装される**機能レベル要件**を `## ADDED Requirements` として差分specに書き、実装とともにアーカイブでbaselineへマージしていく。要件名がbaselineと重複しないよう、baselineは契約レベル、Changeは機能レベルで分担する。
- この運用は公式フロー（propose → apply → archive で specs が育つ）と矛盾せず、「実装前に全領域の設計合意を取る」という本プロジェクト要件を満たす。判断の記録は docs/17 にも行う。

## 4. 配置計画

グリーンフィールドであることを踏まえ、以下の配置を確定する。

```text
/home/z/my-project/
├── openspec/          # OpenSpec 2.0（仕様とChange。実装の単一の真実源）
│   ├── config.yaml
│   ├── specs/         # 23能力のbaseline仕様
│   └── changes/       # Phase 1の実装Change（依存順）
├── docs/              # 設計文書（本Phase 0の成果物群、18点）
├── src/               # Phase 1で作成（engine / data / maprender / ui）
├── tools/pipeline/    # データ収集・正規化パイプライン（Node）
├── tests/             # unit / property / golden / e2e
├── scripts/           # 本作業環境での生成スクリプト（レポート生成等）
└── download/          # ユーザーへの納品物（docs/openspecのコピーと総合報告書）
```

- `openspec` と `docs` が設計の真実源。`docs` は読み物（理由・経緯・比較表）、`openspec` は規範（ SHALL で書かれた契約）と役割を分ける。両者の矛盾は `openspec` を優先し、docs を修正する。
- 実装コード（`src/`）は Phase 1 の最初のChange（simulation-clock）で作成する。Phase 0 でコードを書かない（要求どおり「仕様レビューが完了した段階で実装可否を判断」するため）。

## 5. 分析から確定した制約

1. **既存制約ゼロ**: 技術選定は完全に自由。ただし本リポジトリはブラウザ向けフロントエンドであり、Phase 1 ではバックエンド常設サーバを持たない（クライアント完結型、docs/09 参照）。
2. **OpenSpec 2.0.0 固定**: 以降の仕様・Changeは v2.0 のフォーマット厳守。`openspec validate --all --strict` をCIゲートとする。
3. **単一コミットの履歴**: 過去の設計意思決定は存在しないため、すべての判断を docs/17（設計レビュー記録・ADR）に記録して将来の参照点とする。
4. **作業環境の性質**: 長時間の常駐プロセスは保証されないため、性能検証（docs/13）は「再実行可能なベンチマークスクリプト」として残し、実測値はスクリプト実行時に記録する方式とする。
