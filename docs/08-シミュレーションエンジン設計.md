# 08. シミュレーションエンジン設計

- 作成日: 2026-11-14
- 状態: 確定（Phase 0 成果物 9/18）
- 規範レベルの契約は `openspec/specs/game-core`, `simulation-clock` を参照。

## 1. 設計原則

1. **UI非依存の純粋なコア**: エンジンは DOM/PixiJS/React を一切 import しない。Node 上でも動く（ベンチマーク・ゴールデンテストのため）。
2. **決定論**: 以下を満たす限り、同一シード＋同一コマンド列は常に同一状態を生む。
   - 数値: float64 の仕様確定演算（`+ - * /`・比較）のみ。ECMAScript仕様上 `Math.sin/cos/exp/log` は「implementation-approximated」で実装間の値が揺れ得るため**シミュ内で禁止**。必要時は整数インデックスのLUT＋線形補間。
   - 乱数: `Math.random` はシード不可のため使用禁止。PCG32 を自前実装し、世界シード＋システム名で派生した子ストリームを用いる。
   - 反復順序: すべてのループは ID 順（配列インデックス順）で固定。Set/Map のイテレーション順はソートしてから使用。
   - 時刻: `Date.now` 等の実時刻をシミュに取り込まない。
3. **データ指向**: 状態は SoA（構造体配列）。ホットパス（移動・戦闘・補給）は配列走査で書き、オブジェクト割当はtick内でゼロに近づける。
4. **コマンド駆動**: 状態変更はすべてコマンド。検証（validate）→適用（apply）の二段階。無効コマンドは適用せず理由を記録。
5. **システムのスケジュール制**: 各システムは `{name, cadence(daily/weekly/monthly), offset, enabled}` でスケジューラに登録。処理頻度・重要度に応じた更新制御（要求どおり「全国家・全ユニットを毎Tick更新しない」）。

## 2. コア構成

```text
src/engine/
├── core/
│   ├── rng.ts            # PCG32実装・子ストリーム派生
│   ├── num.ts            # clamp/lerp/安全な除算ヘルパ（決定論保証）
│   ├── lut.ts            # 整数インデックス関数テーブル（必要時）
│   ├── state.ts          # WorldState コンテナ（ストア集合）
│   ├── command.ts        # コマンド型・レジストリ・検証・適用
│   ├── scheduler.ts      # cadence/offset によるシステム実行制御
│   └── trace.ts          # 計算根拠（contributors）型とヘルパ
├── clock/                # tick進行・日付変換・速度状態
├── map/                  # プロヴィンスストア・隣接グラフ
├── country/ scenario/ military/ combat/ logistics/
├── economy/ population/ politics/ diplomacy/ research/
├── ai/                   # 週次思考・分散スケジュール・判断ログ
├── events/               # 条件DSL評価・MTTH
└── save/                 # スナップショット・シリアライズ・移行
```

- **WorldState**: `{ tick, seed, rng[], stores..., derivedCache }`。`derivedCache` は再計算可能な値のみ（隣接コスト・補給距離等）を持ち、セーブには含めない（INV-8 は復元後の再計算と整合）。
- **コマンドライフサイクル**: `queue`（受付）→ tick境界で `validate`（現状態に対する妥当性）→ `apply`（状態変更・trace記録）→ `journal`（uid, issuer, 結果）。uid は `(issuerId, seqNo)` で二重適用を防ぐ（INV-6）。

## 3. スケジューラと更新制御

| cadence | 対象 | 分散方式 |
| --- | --- | --- |
| daily | 移動・戦闘・補給減衰・装備損耗 | 毎tick（ただしプロヴィンス/ユニット単位の稼働チェック: 戦争関与なしは戦闘処理スキップ） |
| weekly | AI思考・政治・外交・補給再計算 | `tick % 7 == hash(systemName) % 7` でオフストリーム。AIは国家ID % 7 でさらに分散 |
| monthly | 経済・人口・集計 | 月初の単一tick。国家順はID順固定 |
| on-dirty | 補給グラフ再計算・国境描画データ | 損壊・占領・講和イベントでdirtyフラグ → 次tick先頭で再計算 |

- 250国家・20kプロヴィンス規模では、日次処理を「戦争関与国家のみ」「移動中ユニットのみ」に絞り、週次AIを7日間に分散、月次経済を国別の逐次処理にする。**実測は docs/13 のベンチマークで行い、目標値は未計測のまま確定しない**。

## 4. 決定論の検証方法

1. **ハッシュアンカー**: 定間隔（毎月末）で状態ハッシュ（主要ストアの逐次ハッシュ）を計算・記録。
2. **リプレイ検証テスト**: seed＋コマンド列を2回実行し、全アンカーのハッシュ一致を確認（CI必須）。
3. **セーブ/ロード検証**: 任意tickでセーブ → ロード → 続行 → 元の（セーブなし）実行とハッシュ一致（INV-8）。
4. **プロパティテスト**: fast-check で不変条件（負の在庫なし・隣接対称・貨幣保存則・所有/支配整合）をランダムシードで検証。

## 5. UI・エンジンの分離

- エンジンは Web Worker 内で稼働。UIスレッドとは「コマンド送信」「状態スナップショット受信（ダブルバッファ）」の2経路のみ。
- スナップショットは全体複製ではなく**差分パッチ**（変更ストアの変更範囲）を低頻度（UIフレーム間引き）で送る。20kプロヴィンスでも毎フレーム全複製はしない（差分レンダリングの前提）。
- SharedArrayBuffer は COOP/COEP が必要なため、MVPは使用しない（postMessage 転送）。マルチスレッド化（AI専用Worker等）は Phase 4 以降の性能実測後に判断（判断 D-006）。
- トレース要求: UIが「この師団の戦闘力の根拠」を要求 → エンジンが該当エンティティのみ再計算して返す（常時トレース生成は性能上避ける）。

## 6. 永続化の分離

- エンジンはセーブ形式を知らない。`save/` が WorldState の直列化だけを担当し、IndexedDB・ファイル出力はUI層のストレージアダプタが担う。
- 直列化は「ストアごとの typed array → msgpack（@msgpack/msgpack、BigInt非使用のため既定設定で可）」。Header に version/schemaHash。移行は `migrations/` の連鎖。
- 復元時は derivedCache を再計算し、整合チェック（負値・範囲外・参照切れ）を行う。違反セーブは拒否し理由を表示する。

## 7. 拡張性（MOD・シナリオ）

- コンテンツ（財・産業・技術・イベント・方針・シナリオ・ローカライズ）はすべて宣言データ（YAML/JSON）で、ロード時に数値インデックスへ解決。エンジンコードにコンテンツ定数は存在しない。
- MODはパック単位で読み込み、スキーマ検証・参照整合検証・チェックサム検証を通ったもののみ適用。実行コード（JSスクリプトMOD）はMVPでは提供しない（セキュリティ要件、判断 D-007）。

## 8. 将来のマルチプレイヤーを見据えた制約

- 決定論コア＋コマンドジャーナルにより、ロックステップ同期（コマンド列の共有）が技術的に可能な構造を維持する。
- ただしMVPでは一切の通信コードを持たない。Phase 5 の実現可能性調査（遅延・再同期・タイムスライス）で判断する。
